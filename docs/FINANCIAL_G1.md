# Cedar financial G1 implementation

Task 004 authorizes this bounded working slice. Accepted v1.0 success schemas/enums/cookie name remain unchanged; no v1.1 proposal is promoted. Built on latest main 87e062539ba453bd9a99be70fa4386cea634bd86 after GitHub confirmed G0 PR1 and AI foundation PR2 merged. No AI/frontend file is modified or AI call added. ## Accounting and persistence

Migration 0003_financial_g1 follows preserved 0002_proactive_g0. New Cedar tables: customers, accounts, beneficiaries, demo_sessions, ledger_accounts, ledger_journals, ledger_entries, transfers, transfer_idempotency, banking_events, payment_instructions, transfer_attempts, payment_evidence. New private tables: network_policy and recipient_credits. G0's six Veriq/two Cedar tables remain intact; total 23 tables across the three schemas. No complaints or staff tables.

Account balance and all ledger amounts are BIGINT kobo, positive command amounts with a 9000000000000000-kobo synthetic application bound. Pydantic rejects floats, bools, strings, zero and negatives. PostgreSQL positive/side/nonnegative checks and posting/state functions enforce invariants below API validation. The server selects the active account owned by its trusted session bank/customer, not a client account/customer parameter. One account per customer is a bounded G1 design choice.

Opening synthetic funds: debit DEMO_CASH_ASSET and credit the customer DEPOSIT_LIABILITY, 10000000 kobo. Transfer: debit that deposit liability and credit OUTGOING_TRANSFER_CLEARING by the same amount. The debit decreases customer available balance atomically. This is sender-side simulated accounting, not complete interbank settlement. S0 confirmation does not imply a second sender debit or full clearing settlement.

Each posted journal has exactly two appropriate entries in this small slice. Deferred constraint triggers enforce count, equal debit/credit sums, journal amount, correct ledger sides/account, transfer amount/account match and available balance equal to the deposit-ledger projection. UPDATE/DELETE triggers enforce append-only journals/entries/accounts and immutable events/evidence/idempotency/attempt facts; a transaction-ID guard prevents later insertion into an existing posted journal. No runtime direct ledger-write or account-update grant exists. Reviewed SECURITY DEFINER functions lock the owned account and post one validated debit under fixed pg_catalog/pg_temp search paths and fully qualified table names; PUBLIC execution is revoked. A unique bank/transfer journal key prevents reposting. Administrative migrations/seed can initialize opening journals, and tests verify even administrative ordinary UPDATE/DELETE is rejected. Superuser compromise/trigger disabling is outside isolation claims.

Reversal kinds/commands are deliberately absent. A future authorized reversal must use a new compensating journal and explicit financial-evidence policy; never mutate a posted debit. Status query/reveal, failure/reversal posting and complex reconciliation are not implemented.

## Request, concurrency and durability

The command revalidates the typed input, hashes the idempotency key, fingerprints normalized material request fields and serializes the (bank, customer, key hash) scope with a PostgreSQL transaction advisory lock. Same key/same payload returns the original transfer ID and current persisted state; materially different payload returns deterministic IDEMPOTENCY_CONFLICT/409. Omitted and empty narration normalize identically. Different customers/banks have separate key spaces. Failed validation does not consume a key or post a debit.

Account locking serializes independent keys to prevent overspending. In one Cedar transaction: create transfer, append CREATED/VALIDATED events, post balanced debit through the database function, append DEBIT_POSTED event, insert immutable idempotency record and durable payment instruction. Failure before commit rolls all effects back. Network calls occur after commit, outside this transaction. A repeated POST need not reproduce an old snapshot of progress; it returns the original identity with current legitimately known stage/outcome.

The dispatcher claims queued/retry/expired instructions using FOR UPDATE SKIP LOCKED, generation fencing and a 60-second lease; five attempts with bounded delays 5/15/45/135 seconds, capped180. It appends immutable numbered attempts. SUBMITTED stage is recorded once. Request POST tries immediate dispatch; an autonomous separate worker polls every second while idle and recovers interrupted instructions. Database claim failure needs process-supervisor restart; no supervisor/alerts are deployed. Exhausted failures retain debit/instruction and UNKNOWN, never invent failure or reversal. A future operator retry policy requires approval.

Core transfer facts, beneficiary and route/service are immutable. Cedar banking_events form an append-only sender-visible history/outbox with occurred/observed times, source, route/service, transfer ID, stage and known outcome. They are not yet delivered through a new event API or fed into G0's metric-only port. Payment instructions are the mutable durable delivery cursor; raw events remain immutable. No unsupported customer fields are added.

## Network and evidence boundary

Cedar's dispatcher consumes an internal PaymentNetwork capability, injected only by composition. A PaymentRequest contains the immutable intended instruction, never scenario controls. SyntheticNetwork has only simulator-role sessions. It stores a unique private recipient credit per bank/transfer with instruction identity/digest and the selected private scenario. Replay, including crash after private commit/before sender ack, returns the same permitted observation without a second credit. Changed instruction content under that identity is rejected. Private policy is administrator-only writable; ordinary Cedar and Veriq roles cannot read it or private credits.

S0 commits the private synthetic credit and returns CREDIT_RESPONSE. Only after Cedar receives, validates and persists matching source/transfer/instruction/beneficiary/amount evidence does it move ACKNOWLEDGED→COMPLETED and CREDIT_CONFIRMED. S2 commits Elm's private credit but drops the synthetic success response and emits only OBSERVED_TIMEOUT; Cedar records RESPONSE_TIMEOUT/UNKNOWN. It receives no credited boolean, private scenario or recipient ledger value. Private policy changes do not alter a previously recorded instruction result. S2 is limited to Elm/G2; Birch/G3 remains the normal comparison path. All transport is in-process synthetic behavior, not a real bank/network protocol or real-time network timer.

Completion checks an unexpired current generation and evidence identity. Duplicate, expired, stale or delayed messages cannot regress a completed transfer or overwrite finality. Database state guards reject invalid stage transitions, credit confirmation without matching eligible persisted response, removal of confirmation evidence, or financial finality inferred from timeout. The full v1.0 stage/outcome enums are preserved, but unsupported transitions/status-query/reversals remain unreachable. No reveal endpoint is registered. Later authorized verification is a separate task.

## Customer API and demo auth

Only GET accounts/me, GET banks, POST name-enquiries, POST transfers and GET transfers/{transferId} under /v1/cedar are added. Exact accepted closed success objects and arrays are retained. Name enquiry uses fictional beneficiary reference data, not private financial state. All five operations use APIKeyCookie sessionAuth/cedar_demo_session, resolving a random opaque token's SHA-256 hash and database-time expiry to bank/customer. Unknown/expired/missing tokens get401; another customer's transfer gets404. No anonymous/default-global-customer bypass, browser-supplied identity, auth-mint HTTP route or proposed session lifecycle is added.

Private ENVIRONMENT=test CLI seed/mint-session/arm/replay uses separately supplied MIGRATION_DATABASE_URL. Session files use exclusive create, mode0600, *.session.json ignore and one-hour expiry; no token is printed in normal CLI output. API/worker runtime Settings has no migration credential field. Cookie auth is deliberately limited: no browser login/refresh/revocation journey or cross-origin frontend integration exists. POST requires JSON and rejects explicitly foreign Origin; no CORS bypass is added. Responses use no-store and structured logs omit cookie/body/raw errors/private data. A later real browser identity journey must issue secure HttpOnly/SameSite cookies over HTTPS. Backend process compromise is not isolated by shared credentials/packages; no RLS or network-auth/production-readiness claim.

Explicit grants: Cedar SELECT on its financial/reference/session/ledger data; INSERT/UPDATE on transfers/instruction cursors; INSERT on idempotency/events/attempts/evidence; EXECUTE on reviewed lock/debit/projection helpers. No direct balance/ledger DML. Simulator SELECT policy and SELECT/INSERT credits, no runtime policy mutation. Veriq grants unchanged; no Cedar/private access. AI/frontend receive no database credentials or financial function grants; actual unprivileged test roles are denied ledger access/function execution. A shared process remains privileged relative to a production multi-service boundary.
