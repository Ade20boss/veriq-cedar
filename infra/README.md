# Local database infrastructure

Task 002 supplies compose.yaml, .env.example and postgres/ role/grant scripts. See ../apps/backend/README.md for the complete sequence: configure ignored environment files, start PostgreSQL, apply Alembic, grant runtime access, run readiness/tests. The official image is pinned by digest; no banking data is seeded.

Only 127.0.0.1 is published. The PostgreSQL administrator/migrator and three runtime roles are distinct. First-volume bootstrap creates runtime roles; the explicit post-migration grant script grants own-schema USAGE, version-table SELECT and the explicit G0/G1 table/function allowlists from Tasks 003/004. Apply migration head before reapplying grants. There is no cross-domain or private-table grant and no blanket future-table grant. Future business migrations require explicit per-table privileges. Do not infer full security isolation from schema/package separation or the migration superuser.

Compose execution was unavailable here (no Docker; Podman runtime path read-only). A real isolated PostgreSQL 16.2 test process was used instead, then stopped. No database service was deployed or left running. Do not delete existing volumes or reinitialize an existing database without explicit authorization.

Task 004 migration 0003_financial_g1 adds Cedar financial/auth/reference tables, private synthetic policy/credit tables and database accounting/state triggers. Reapply grants after migration head. Cedar runtime can select ledger/account data but cannot directly insert/update/delete ledger facts or update balances: its restricted SECURITY DEFINER debit function performs validated posting atomically. Veriq receives no new Cedar/private grants; simulator receives private policy SELECT and private credit SELECT/INSERT only. Function PUBLIC execution is revoked and search paths are fixed. No role is granted unrestricted schema CREATE or broad future-table privileges. Migration/seed administration remains privileged and must stay outside runtime URLs.
